# LightningLab r10.79 — افزایش حساسیت اسکن رعدوبرق و مسیر AI آفلاین

## اصلاح واقعی این نسخه
در مسیر اصلی MediaCodec همه فریم‌های رمزگشایی‌شده استفاده می‌شوند. اما مسیر جایگزین MediaMetadataRetriever قبلاً هر ۱۰۰ میلی‌ثانیه یک فریم می‌گرفت. فلاش‌های کوتاه ممکن بود میان این نمونه‌ها بیفتند و بررسی حرکت جبران‌شده DayLine هم در آن مسیر اجرا نمی‌شد.

### تغییرات
1. مسیر fallback برای ویدئوهای تا ۲ دقیقه هر ۳۳ میلی‌ثانیه نمونه می‌گیرد؛ برای ۲ تا ۱۰ دقیقه ۵۰ میلی‌ثانیه و برای ویدئوهای بلندتر دست‌کم ۱۰۰ میلی‌ثانیه.
2. حداکثر بودجهٔ نمونه‌برداری حدود ۳۰٬۰۰۰ فریم است، تا هزینهٔ decode در ویدئوهای بسیار بلند بی‌نهایت بالا نرود.
3. DayLine (تفاضل روشنایی همراه با جبران جابه‌جایی تصویر) در fallback هم وقتی ابعاد تصویر کافی است اجرا می‌شود. فریم‌های بدون residual معتبر مثل لرزش دوربین، بهتر از قبل قابل رد شدن‌اند.
4. فریم Bitmap بعد از خواندن پیکسل‌ها حتی در رخداد خطا recycle می‌شود.
5. ۵ تست JVM جدید برای cadence کوتاه/میانی/بلند، محدودیت نمونه، overflow و ابعاد لازم برای motion verification اضافه شد.
6. مسیر MediaCodec، قرارداد رخداد، sidecar بازبینی و مدل‌های قبلی حذف یا جایگزین نشده‌اند.

## احتیاط علمی و فنی
- افزایش نرخ نمونه‌برداری fallback می‌تواند **احتمال جاافتادگی فلاش کوتاه را کاهش دهد** اما این ادعا از نظر عددی با دیتاست خارجی هنوز ارزیابی نشده.
- getScaledFrameAtTime نزدیک‌ترین فریم واقعی را برمی‌گرداند؛ نمونه‌های ۳۳میلی‌ثانیه‌ای لزوماً فریم جدید ندارند.
- DayLine یک الگوریتم هندسی است، نه مدل آموزش‌دیده و نه اثبات CG/IC.
- مسیر fallback ممکن است نسبت به قبل CPU، باتری و زمان بیشتری مصرف کند؛ نیاز به benchmark عملی روی دستگاه دارد.
- فقط با RGB نمی‌توان قطبیت، شدت جریان یا انرژی فیزیکی را قطعی تعیین کرد.

## برنامهٔ دقیق ML برای افزایش واقعی Precision/Recall
### چرا مدل فعلی به تنهایی کافی نیست؟
مدل زمانی فعلی کلاس‌های هفت‌گانه Brixton را رتبه‌بندی می‌کند. این مجموعه **کلاس منفی «صاعقه وجود ندارد»** ندارد؛ بنابراین نمی‌توان از max softmax این مدل برای رد رخدادهای کاذب استفاده کرد.

### مدل پیشنهادی دو مرحله‌ای آفلاین
- مرحلهٔ ۱: Detector/FlashAnalyzer/DayLine کاندیداها را با حساسیت بالا کشف کنند.
- مرحلهٔ ۲: یک **Binary Verifier** جدا با برچسب‌های `lightning` و `non_lightning` روی پنجرهٔ ۸ فریمی اجرا شود.
- مرحلهٔ ۳: raw heuristic score، verifier score، type model و رأی انسان در UI و CSV/JSON **مجزا** حفظ شوند.
- دیتاست negative: نور خودرو، فلاش دوربین، چراغ LED، scene cut، انعکاس، ساختمان، آفتاب و اشباع لنز، نویز دوربین، آتش‌بازی و نور مصنوعی.
- تقسیم داده بر اساس ویدئو و محل/دوربین؛ همه نمونه‌های یک رخداد در یک split قرار بگیرند.
- threshold و calibration صرفاً در validation انتخاب، test مستقل بدون tuning نهایی استفاده شود.
- از حذف خودکار رخدادها بر اساس مدل اعتبارسنجی‌نشده جلوگیری شود: ابتدا حالت **assist / review priority** و فقط بعد از آزمون مستقل، امکان filter.
- TFLite آفلاین و روی گوشی اولویت دارد. تحلیل آنلاین تنها **با رضایت و ارسال آگاهانهٔ رسانه** و به‌صورت اختیاری؛ شبکه یک نقطه شکست است و حریم خصوصی اهمیت دارد.

### معیارهای ارزیابی
- event recall روی ویدئوهای کامل برچسب‌خورده؛ false alarms/hour در صحنه‌های منفی؛ precision، F1، latency per minute و RAM و باتری.
- تفکیک روز/شب، کوتاه/بلند، landscape/portrait و دوربین‌های متفاوت.
- مقایسهٔ paired بین r10.78 و r10.79 روی همان فایل‌های مرجع، سپس مدل verification.

## کارهای باقی‌مانده
1. پیاده‌سازی dataset generator و training برای مدل binary شامل negativeها.
2. خروجی مدل TFLite دارای checksum و contract `[1,8,224,224,3] -> [1,2]` و UI import مستقل.
3. ادغام opt-in مرحلهٔ AI verifier با نتایج اسکن و خروجی گزارش، بدون حذف خودکار رخداد.
4. benchmarking و regression روی گوشی‌های واقعی، به‌خصوص fallback.
5. تهیهٔ نمونه‌های مستقل قانونی و مشارکت ناظران برای annotation.
