# فاز ۲.۲۴ — بازیابی امن مدل‌های آفلاین

## مسئله

در نسخه‌های قبلی، واردکردن مدل با سه فایل انجام می‌شد: فایل فعال، فایل موقت با پسوند `.importing` و نسخه پشتیبان با پسوند `.previous`. اگر سیستم‌عامل برنامه را دقیقاً بعد از انتقال مدل قبلی به فایل پشتیبان متوقف می‌کرد، ممکن بود فایل فعال وجود نداشته باشد. همچنین شروع واردکردن بعدی می‌توانست نسخه پشتیبان باقی‌مانده را پیش از بازیابی حذف کند.

## تغییر این فاز

- کلاس مستقل `ModelFileRecovery` برای بازیابی تراکنش نیمه‌تمام اضافه شد.
- هنگام راه‌اندازی، هر چهار مدل مستقل بررسی می‌شوند: جنس ابر، ویژگی‌های ساختاری، جداسازی دودویی ابر و تفکیک هفت‌کلاسه پدیده‌های جوی.
- اگر مدل فعال معتبر باشد، نسخه پشتیبان کهنه پاک می‌شود.
- اگر مدل فعال خراب باشد و نسخه پشتیبان موجود باشد، مدل قبلی بازگردانده و دوباره بارگذاری می‌شود.
- اگر برنامه پیش از انتقال فایل موقت متوقف شده و فایل فعال وجود نداشته باشد، نسخه پشتیبان مستقیماً بازیابی می‌شود.
- پیش از شروع واردکردن مدل جدید نیز وضعیت تراکنش قبلی تعیین تکلیف می‌شود؛ نسخه پشتیبان تا زمان اعتبارسنجی مدل فعال حفظ می‌شود.
- سه تست واحد برای مدل معتبر، مدل خراب با نسخه پشتیبان و توقف بین دو مرحله انتقال اضافه شد.

## محدوده و محدودیت

این تغییر فقط پایداری نصب/جایگزینی مدل را بهتر می‌کند. مدل جدید آموزش نمی‌دهد و کیفیت علمی تشخیص را افزایش نمی‌دهد. فایل‌های TFLite باید همچنان با اسکریپت‌های آموزش و قرارداد دقیق ورودی/خروجی ساخته شوند.

## وضعیت اعتبارسنجی این بسته

- اسکریپت‌های Python با `py_compile` بررسی شدند.
- اعتبارسنجی بانک دانش جوی با موفقیت اجرا شد.
- تست‌های Kotlin جدید به سورس افزوده شده‌اند؛ اجرای Gradle/Android unit tests در محیط ساخت فعلی ممکن نبود، چون Gradle و Android SDK در دسترس نبودند. اجرای آن‌ها در GitHub Actions لازم است.
